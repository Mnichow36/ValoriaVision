# Valoria Vision — R7.2 / Bêta
## Écran cible Rapprochements et qualification automatique des transactions

**Date de décision : 01/09/2026**

## 1. Décision produit

La maquette de l'écran **Rapprochements** validée le 01/09/2026 devient la **référence UI cible pour la bêta**.

Le développement ne doit pas repartir d'une nouvelle interface : il doit implémenter le moteur métier dans cette structure, avec les adaptations nécessaires pour la qualification automatique des transactions sans prévision, les propositions de rapprochement, l'explicabilité du score et les cas de rapprochement étendus.

Structure cible de l'écran :

- zone de synthèse / KPI ;
- liste **Transactions à rapprocher** ;
- liste **Prévisions à traiter** ;
- panneau **Proposition de rapprochement** ;
- score de correspondance ;
- contrôles expliquant la proposition ;
- actions de validation, ignorance et mode manuel.

## 2. Principe métier : contrôle automatique à l'intégration

Toute transaction réelle intégrée dans Valoria Vision, qu'elle provienne d'un import bancaire ou d'une saisie manuelle, doit être soumise automatiquement au moteur de rapprochement.

Le moteur recherche les occurrences prévisionnelles compatibles et calcule un score de concordance.

Critères minimaux à prendre en compte :

- compte bancaire ;
- sens Débit / Crédit ;
- montant et tolérance ;
- date et tolérance ;
- libellé ;
- catégorie ;
- bénéficiaire / émetteur si disponible ;
- référence bancaire / identifiant externe si disponible ;
- historique de rapprochements similaires lorsque pertinent.

## 3. Résultats possibles du moteur

### 3.1 Concordance forte

Si le score dépasse le seuil de rapprochement automatique et qu'aucune ambiguïté significative n'existe :

- le rapprochement peut être créé automatiquement ;
- le statut doit indiquer qu'il s'agit d'un rapprochement automatique ;
- la décision doit rester traçable, explicable et réversible.

### 3.2 Concordance probable ou ambiguë

Si une ou plusieurs correspondances plausibles existent mais nécessitent une décision utilisateur :

- Valoria Vision crée une **proposition de rapprochement** ;
- la proposition est affichée dans le panneau dédié ;
- elle passe dans la population **À vérifier / Propositions auto** ;
- l'utilisateur peut valider, ignorer ou basculer en mode manuel.

L'utilisateur ne doit pas avoir à rechercher lui-même les deux éléments lorsque le moteur peut déjà proposer un rapprochement probable.

### 3.3 Aucune concordance plausible

Si aucune prévision ou occurrence compatible n'est trouvée :

- la transaction est automatiquement qualifiée **Réalisée sans prévision** ;
- aucune action manuelle obligatoire n'est demandée ;
- elle ne doit pas encombrer la liste principale des éléments nécessitant une action ;
- elle reste consultable et traçable ;
- elle peut être réévaluée automatiquement si les données prévisionnelles évoluent ultérieurement.

Le statut **Réalisée sans prévision** signifie : « aucune prévision correspondante connue actuellement ». Il ne constitue pas une exclusion définitive du moteur.

## 4. Philosophie d'usage : traitement par exception

Le module Rapprochements doit fonctionner comme un système de **contrôle par exception**.

L'utilisateur ne doit pas avoir à traiter manuellement la majorité des opérations bancaires.

Les populations fonctionnelles principales sont :

- **Rapprochées** : concordance confirmée ou automatique ;
- **À vérifier / Propositions auto** : correspondance probable nécessitant une décision ;
- **Prévisions ouvertes** : occurrence prévue sans réalisation trouvée ;
- **Réalisées sans prévision** : transaction réelle sans occurrence correspondante connue.

L'effort utilisateur doit se concentrer principalement sur les propositions ambiguës et les anomalies.

## 5. KPI cibles

La zone de synthèse doit présenter des indicateurs cohérents avec le moteur, par exemple :

- **À vérifier** ;
- **Prévisions ouvertes** ;
- **Sans prévision** ;
- **Rapprochées**.

Le clic sur **Sans prévision** doit permettre de consulter les transactions concernées, sans obligation de les qualifier manuellement une par une.

## 6. Panneau Proposition de rapprochement

Le panneau de droite de la maquette est retenu comme composant central de décision.

Il doit afficher :

- transaction(s) réelle(s) sélectionnée(s) ;
- prévision(s) associée(s) proposée(s) ;
- score de correspondance ;
- explication du score ;
- écarts de montant ;
- écarts de date ;
- concordance du compte ;
- concordance du sens ;
- similarité de libellé ;
- autres critères ayant contribué à la décision.

Exemple d'explicabilité :

- même compte : OK ;
- montant identique : écart 0,00 € ;
- date : +1 jour ;
- libellé fortement similaire ;
- rapprochement similaire observé précédemment.

Le moteur ne doit pas seulement produire un score : il doit pouvoir expliquer pourquoi une proposition a été faite.

## 7. Cas N↔N

La conception doit rester compatible avec les cas :

- 1 transaction ↔ 1 prévision ;
- 1 transaction ↔ N prévisions ;
- N transactions ↔ 1 prévision ;
- N transactions ↔ N prévisions.

Le panneau de proposition doit, dans ces cas, afficher les membres du groupe, les totaux prévus, les totaux réalisés et l'écart global.

## 8. Réévaluation automatique

Une transaction qualifiée **Réalisée sans prévision** doit pouvoir être réanalysée si :

- une nouvelle récurrence est créée ;
- une occurrence prévisionnelle est ajoutée ;
- une prévision est modifiée ;
- les paramètres du moteur de rapprochement sont modifiés ;
- une nouvelle donnée métier améliore la concordance.

Aucune qualification ne doit empêcher une future proposition pertinente.

## 9. Détection de récurrence potentielle

Lorsque plusieurs transactions réelles sans prévision présentent un comportement répétitif, Valoria Vision peut proposer :

**« Dépense / recette récurrente détectée — Créer une récurrence ? »**

La création d'une récurrence doit toujours nécessiter une validation utilisateur.

Le système ne doit jamais créer silencieusement une récurrence à partir d'un simple motif détecté.

## 10. Exigences R7.2 ajoutées

### RME-17 — Qualification automatique à l'intégration

Toute transaction réelle intégrée doit être automatiquement soumise au moteur de rapprochement. Selon le niveau de confiance, elle est :

- rapprochée automatiquement ;
- proposée **À vérifier** ;
- ou qualifiée **Réalisée sans prévision**.

Cette dernière qualification reste réévaluable.

### RME-18 — Détection de récurrence potentielle

Les transactions répétitives sans prévision peuvent donner lieu à une proposition de création de récurrence, sans création automatique sans accord utilisateur.

## 12. Règle de non-régression

Aucune logique de rapprochement ou de qualification ne doit :

- supprimer une transaction réelle ;
- modifier son montant, sa date, son compte ou son sens ;
- masquer une ambiguïté comme un rapprochement certain ;
- empêcher une réévaluation future ;
- rendre le traitement manuel obligatoire pour les transactions sans prévision ;
- créer automatiquement une récurrence sans validation utilisateur.
